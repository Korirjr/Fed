# القرارات المصيرية في Nova

القرار المصيري هو القرار الذي يصعب أو يكلف كثيراً الرجوع عنه بعد أن يُبنى عليه كود أو تُخزَّن عليه بيانات أو يعتمد عليه مستخدمون.
القرارات الأخرى (القابلة للرجوع) نتخذها بسرعة ونغيّرها عند الحاجة.

القاعدة: **نُبطئ في المصيرية، ونُسرع في غيرها.**

---

## أولاً: قرارات مصيرية يجب حسمها الآن

### 1. عزل كود المستخدمين (الأمان)
- **الوضع الحالي:** `bannaa/backend` ينفّذ أوامر الـ Agent والكونسول **مباشرة على السيرفر** بلا عزل (انظر `bannaa/README.md`، قسم Security).
- **لماذا مصيري:** أي ثغرة هنا تعني اختراق السيرفر وكل مشاريع المستخدمين. وطريقة العزل تحدد شكل `runner.rs` و`workspace.rs` بالكامل.
- **القرار المقترح:** لا يُفتح Nova لأي مستخدم خارجي قبل نقل التنفيذ إلى Daytona (بيئة لكل مشروع). نكتب طبقة `Sandbox` واحدة في الكود بحيث يكون Daytona تنفيذاً لها، وتبقى النسخة المحلية للتطوير فقط.

### 2. لغة محرّك الـ Agent: Rust أم TypeScript؟
- **الوضع الحالي:** `DECISIONS.md` يقول «TypeScript»، لكن المحرّك الموجود فعلاً مكتوب بـ Rust (`bannaa/backend/src/agent.rs`).
- **لماذا مصيري:** كل أداة جديدة تُضاف للـ Agent تُكتب بلغة واحدة؛ كلما تأخر الحسم زادت كلفة إعادة الكتابة.
- **الخيارات:**
  - *Rust:* موجود ويعمل، خدمة واحدة أقل، أداء جيد.
  - *TypeScript:* مكتبة Anthropic الرسمية وzod، أسرع في إضافة الأدوات، وأسهل لتوظيف المطورين.
- **القرار المقترح:** يُحسم قبل إضافة أي أداة جديدة، ويُحدَّث `DECISIONS.md` ليطابق الواقع.

### 3. من يدفع تكلفة Claude؟
- **الخيارات:** مفتاح المستخدم نفسه (BYOK)، أو رصيد من Nova (اشتراك/نقاط)، أو الاثنان.
- **لماذا مصيري:** يحدد هل نحتاج نظام عدّ استهلاك (metering) وفوترة وحدود لكل مستخدم من اليوم الأول، ويحدد نموذج العمل كله.
- **القرار المقترح:** رصيد من Nova مع حدود يومية، لكن نسجّل استهلاك التوكنز لكل مشروع ولكل مستخدم من الآن مهما كان القرار (التسجيل رخيص، وإضافته لاحقاً للبيانات القديمة مستحيلة).

### 4. نموذج البيانات والهوية
- **ما يجب حسمه:** شكل الجداول الأساسية: `users` ← `organizations`؟ ← `projects` ← `workspaces` ← `runs/messages`، ونوع المعرّفات (UUID v7 مقترح)، ومزوّد تسجيل الدخول.
- **لماذا مصيري:** تغيير المفاتيح والعلاقات بعد وجود بيانات حقيقية مكلف جداً. وإضافة «الفرق/المنظمات» لاحقاً لنموذج مبني على مستخدم فردي من أصعب الترحيلات.
- **القرار المقترح:** نضع `organization` من البداية حتى لو كان لكل مستخدم منظمة واحدة تلقائياً.
- **الوضع الحالي:** المشاريع والمحادثات ملفات في `BANNAA_DATA_DIR`؛ مقبول للنموذج الأولي فقط.

### 5. أين يعيش كود المستخدم، ومن يملكه؟
- **الخيارات:** في مستودع GitHub يملكه المستخدم، أو في تخزين Nova مع تصدير اختياري.
- **لماذا مصيري:** يحدد الثقة (هل المستخدم محبوس في Nova؟) والنسخ الاحتياطي والتسعير.
- **القرار المقترح:** Git هو مصدر الحقيقة دائماً (مستودع داخلي لكل مشروع)، وGitHub مرآة اختيارية. المستخدم يستطيع تنزيل مشروعه كاملاً في أي وقت.

### 6. موقع البيانات (المنطقة الجغرافية)
- **لماذا مصيري:** نقل قاعدة بيانات ومشاريع المستخدمين بين المناطق لاحقاً مؤلم، وقد تفرض أنظمة حماية البيانات المحلية (مثل PDPL في السعودية) بقاء البيانات في منطقة معيّنة.
- **القرار المقترح:** نحدد السوق الأول، ثم نختار منطقة Google Cloud (وDaytona) الأقرب والمتوافقة، ونبقي Cloud SQL وCloud Run والبيئات في المنطقة نفسها.

### 7. الاسم: Nova أم بنّاء؟
- **الوضع الحالي:** الوثائق تقول Nova، والواجهة والمجلد يقولان «بنّاء».
- **لماذا مصيري:** النطاق (domain)، العلامة التجارية، اسم GitHub App، روابط المستخدمين. تغييره بعد الإطلاق يضيّع كل ذلك.
- **القرار المقترح:** يُحسم الاسم ويُحجز النطاق قبل أي إطلاق عام، ثم يُوحَّد في الكود والوثائق.

## ثانياً: قرارات قابلة للرجوع (لا نُطيل التفكير فيها)

| القرار | لماذا يمكن تغييره لاحقاً |
| --- | --- |
| Cloud Run الآن ثم GKE | الخدمات في حاويات؛ النقل لا يغيّر الكود |
| Next.js للموقع | واجهة فقط، تتحدث مع API |
| syntect أو Shiki للتلوين | خلف واجهة واحدة على السيرفر |
| Expo افتراضياً للتطبيقات | خيار لكل مشروع، وNative يُضاف بجانبه |
| Appetize للأجهزة الحقيقية | خدمة خارجية قابلة للاستبدال |
| النموذج المستخدم (`BANNAA_MODEL`) والجهد | متغيّر بيئة |
| Secret Manager | المفاتيح تُقرأ من مكان واحد في الكود |

## ترتيب الحسم المقترح

1. **العزل (1)** و**لغة الـ Agent (2)**: يمنعان تراكم كود سيُعاد كتابته.
2. **نموذج البيانات (4)** و**ملكية الكود (5)**: قبل أول مستخدم حقيقي.
3. **التكلفة (3)**، **المنطقة (6)**، **الاسم (7)**: قبل الإطلاق العام.

عند حسم أي قرار: يُنقل إلى جدول `DECISIONS.md` مع تاريخه وسببه في سطر واحد.
